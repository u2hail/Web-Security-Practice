# Web-Security-Practice

我的 Web 安全学习与靶场实践记录。方向：**Web 渗透 / 安全审计**。

---

## 关于我

物理学本科毕业，此前在制造业从事产线工艺与质量相关工作（良率改善方向），做的核心事情是**从数据里找异常、追根因、推动整改闭环**。转向信息安全后，我发现这两件事的底层逻辑是相通的——都是在复杂的系统里定位问题、验证假设、推动修复。

目前以 Web 安全为主攻方向，系统性推进漏洞原理学习与靶场实战，所有练习过程与报告都归档在本仓库。

**为什么把所有过程都写下来**：安全圈里打过靶场的人很多，但留下完整记录的不多。我更希望这份仓库呈现的是**思考过程**——包括我判断错、卡住、后来想通的地方。面试官和读者看的不该只是"他打通过"，而是"他怎么想的"。

## 我在练什么

按这条主线推进：

```
漏洞原理 → 靶场验证 → 完整渗透流程 → 报告输出 → 真实目标（SRC）
```

**每类漏洞按同一套四问整理**：

| 四问 | 说明 |
|---|---|
| **成因** | 为什么这个漏洞能存在（机制，不是背定义） |
| **利用链** | 从"看到这个功能"到"拿到结果"的完整步骤 |
| **绕过** | WAF / 黑名单 / 编码过滤的绕过方式 |
| **修复** | 要能说出"为什么这样修"，而不只背"参数化查询" |

**我目前的理解**：这四问里，`绕过` 和 `修复` 是分水岭——会打不代表会讲，会讲不代表会守。

**四份报告串起来是一条完整的"信息通道"主线**：

```
有回显位        → 联合查询      （Less-1/2/3，1 个请求拿数据）
无回显但报错     → 报错注入      （Less-5，受约 30 字符回显上限）
报错也不回显     → 布尔盲注      （Less-8，靠页面长度差异，7 个请求/字符）
```

**再加上注入点位置的两种形态**：GET（URL 参数）与 POST（请求体，Less-11）。

**报告里的攻击链**：判断数据库类型 → 判断参数类型 → 确定闭合方式 → `order by` 试列数 → 确认回显位 → 爆库名 → 爆表名 → 爆列名 → 取数据。修复建议部分包含**立即缓解 / 根本修复 / 同类排查 / 验证方法**四层。

### `04-PoC脚本/`

验证与利用脚本（仅用于本地自建靶场）。

**Less-5 · 报错注入**

- **`PoC-5.py`** — 验证报错注入存在：发一次请求，用正则从 `updatexml` 的报错回显中提取 `database()`
- **`EXP-5.py`** — 完整导出 `users` 表：因报错回显仅有约 30 字符上限，用 `group_concat` 把整表压成一个长串，再以 `substr` 按 30 字符分段循环取值，每段校验尾部标记符确认未被截断，最后拼接并校验分隔符数量（13 条数据应得 13 个 `:` 和 12 个 `,`）

**Less-8 · 布尔盲注**（手写算法的过程，四个版本递进）

- **`base-8.py`** — 量基准：对比"条件为真"与"条件为假"两个页面的长度
- **`function-8.py`** — 线性试：ASCII 码从 32 试到 126，每字符约 95 次请求
- **`function2-8.py`** — 跳跃法：探测点 + 步长减半（64/32/16/8/4/2/1），每步要问 2~3 次
- **`function3-8.py`** — **二分法**：维护区间 `low~high`，每次砍一半，每步只问 1 次，7 次锁定任意字符
- **`table_name-8.py`** — 把目标从库名换成表名（子查询 + `group_concat` 把多行压成一行）

**Less-9 · 时间盲注**

- **`EXP-9.py`** — 与 `function3-8.py` 相比**只改了判断函数一处**：从"比页面长度"改成"比响应耗时"，其余框架一行未动

## 一条贯穿始终的结论

四种注入手法不是四个知识点，而是**一条按"每次能拿到多少信息"排序的决策链**：

```
有回显位        → 联合查询      1 个请求拿一行数据
无回显但报错     → 报错注入      约 30 字符/请求（受回显上限限制）
报错也不回显     → 布尔盲注      约 7 个请求/字符
连差异都没有     → 时间盲注      每问一次都要等 sleep，最慢
```

**同样的库名 `security`，四种手法的成本对比**：

| 手法 | 取到库名的成本 |
|---|---|
| 联合查询 | 1 个请求 |
| 报错注入 | 1 个请求 |
| 布尔盲注 | 56 个请求（约 120 秒） |
| 时间盲注 | 56 个请求（**216 秒**） |

**所以遇到注入点的第一件事，不是套用某种手法，而是判断"它给我什么信号"。**
这也是我在 Less-9 的报告里写下的一句话：**通道再窄，只要还有 1 个 bit 能稳定传递信息，数据就能被问出来。**
