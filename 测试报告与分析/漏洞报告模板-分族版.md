# 漏洞报告模板（分族版）

> 配套 `漏洞方法论-总纲.md` 使用。
>
> **为什么要分族**：SQLi 的检测步骤（判断数据库类型 → 闭合方式 → 过滤规则）放到 XSS 上完全没用。
> 每类漏洞的"漏洞检测"章节必须换成该类漏洞自己的检测方法论，否则报告是空转的。
>
> **用法**：复制对应族的模板 → 另存为 `测试报告与分析/XXX报告.md` → 按提示填空 → 删掉所有 `【】` 提示。

---

## 通用规则（所有族都适用）

| 项 | 要求 |
|---|---|
| 截图 | 统一放同级 `images/`，相对路径 `![image-xxx](images/image-xxx.png)` |
| 数据 | **所有结论必须有实测证据**：payload 原文、回显内容、截图 |
| 不写 | 绝对路径（`C:\...`）、编造的数据、"应该可以"之类未验证的推断 |
| 修复 | 必须包含**可执行的验证方法**（复测 payload + 预期结果） |
| 影响 | 分两层：**技术描述**（能做什么）+ **业务影响**（对业务意味着什么） |

# 一、SQL 注入

参考成品：`SQLI-LAB报告-LESS26.md`（285 行）

```markdown
## 漏洞概要
【SQL 注入的本质：应用把用户输入拼进 SQL 字符串，导致数据库无法区分"代码"与"数据"，
  于是数据被当 SQL 语句执行。常见于未使用参数化查询、以字符串拼接构造 SQL 的场景。
  按注入点位置分 GET 型 / POST 型；按信息通道分 联合查询 / 报错注入 / 布尔盲注 / 时间盲注。】

## 漏洞检测
0、判断数据库类型
   【方法：故意传 `'` 制造语法错误，报错原文里往往直接写明数据库名；
     或用 updatexml()、@@datadir、database() 等库特有函数验证】
1、判断数字型还是字符型
   【数字型：`id=1 and 1=1` 与 `id=1 and 1=2` 结果不同即成立】
   【字符型：传 `'` 立即报错，说明参数被引号包裹】
2、判断闭合方式
   【报错位置在 near ''1'' 说明闭合符为 `'`；near '1'')' 说明为 `')`】
3、判断信息通道（有没有回显 / 报错 / 页面差异 / 耗时差异）
   【有回显位 → 联合查询；无回显但报错 → 报错注入；
     只有页面长度差异 → 布尔盲注；连差异都没有 → 时间盲注】
4、判断过滤规则
   【**必须读源码里的过滤函数**，不要靠猜。逐条确认：关键字、空格、注释符、
     引号转义、编码处理分别是什么规则】

## 打靶练习
【按攻击链逐步写，每步：payload 原文 + 观察到的现象 + 由现象得到的判断 + 截图】
【注意：把"卡住的地方"也写进来——判断错、换思路的过程比结论更有价值】

## 总结

### 一、影响与危害
【技术上能做什么（需不需要凭据）→ 本次实测到什么（具体到库/表/字段/行数）
  → 对业务意味着什么（撞库 / 账号冒用 / 合规责任）】
**利用门槛**：【需要什么条件，例如"仅需浏览器与一次 URL 参数修改"】

### 二、修复建议
1、根本修复：【参数化查询——先说清原理：先固定语句结构、再把参数作为纯数据传入】
2、为什么不能用转义/过滤替代：【黑名单是列举已知，攻击面是无限的。这是"堵"不是"隔离"】
3、临时缓解（代码改不动时）：【数据库降权 / 关闭报错回显 / WAF 特征拦截】
4、同类问题排查：【按"是否存在字符串拼接构造 SQL"检索全部接口】
5、修复验证方法：
   【原 payload 复测 + 预期结果】
   【换手法复测：报错 / 布尔 / 时间，确认全部失效——仅拦 UNION 不算修好】

### 三、延伸思考
**卡在哪**：【写过程："我一开始以为…后来发现…"，不要只写结论】
**学到什么**：【能带到下一关的结论】
```

# 二、XSS

> 你的现状：`XSS漏洞原理与利用.md` 里 DOM / 反射 / 存储三种都实操过、有 payload、有截图，
> **但缺四问框架**。这份模板按你已有的内容补齐结构。

```markdown
## 漏洞概要
【XSS 的本质：浏览器无法区分页面里的 <script> 是开发者写的、还是用户数据里带的，
  于是把用户数据当 HTML/JS 解析执行。
  与 SQL 注入同源——都是"代码与数据没分离"，只是失守层从数据库换成了浏览器解析器。】
【分三类，差别在"数据经过哪里"：
  反射型：数据经服务端响应立即回显，不落库
  存储型：数据落库，之后每次访问都触发（危害最大，可打管理员）
  DOM 型：全程在前端，服务端不参与，数据被 JS 写进危险 sink】

## 漏洞检测
0、找输出点（先看数据回了哪里，这是 XSS 检测的第一步）
   【传一个带特征的字符串（如 `xss123` 或 `"><h1>t`），在响应里搜它出现在哪：
     HTML 正文 / 标签属性内 / <script> 内 / URL 里 / 事件处理器内】
1、判断上下文（决定用什么 payload，这一步比 payload 本身重要）
   【HTML 正文   → 需要构造完整标签 <script>alert(1)</script>
     属性值内     → 需要先闭合属性 " onmouseover=alert(1) x="
     <script> 内  → 不能引入新标签，要闭合字符串 ';alert(1);//
     URL 里       → javascript: 伪协议】
2、测过滤规则
   【逐个试：< > " ' ( ) 是被转义、被删、还是被编码（HTML 实体 / Unicode / URL 编码）】
3、测输出编码
   【关键问题：数据是被"编码"了，还是只是被"替换了危险字符"？
     编码是安全的，黑名单不是——找它漏掉的等价写法】
4、区分反射 / 存储 / DOM
   【重复请求看是否稳定触发 → 存储型；只在当前请求回显 → 反射型；
     查看 JS 源码里有危险 sink（innerHTML / document.write / eval）→ DOM 型】

## 打靶练习
【按"找到输出点 → 判断上下文 → 构造 payload → 验证执行"写】
【存储型额外记：载荷落在哪个字段、什么时候触发、谁访问会中招】
【如果做了外带（把 cookie 发到监听端），把监听端收到的内容也截下来】

## 总结

### 一、影响与危害
【技术上能做什么：窃取 Cookie / 会话劫持 / 挂马 / 钓鱼 / 蠕虫式传播 / 打后台管理员】
【本次实测到什么：具体到哪个功能、哪类 XSS、实际拿到了什么（如 document.cookie）】
【对业务意味着什么：用户账号被盗 / 管理员被拿下导致后台沦陷 / 用户被钓鱼】
**利用门槛**：【反射型需要诱导点击；存储型无需交互，只要有人访问页面】

### 二、修复建议
1、根本修复：【**按输出上下文编码**，不是统一转义。
   HTML 正文用 HTML 实体编码，JS 字符串用 JS 转义，URL 用 URL 编码。
   原理：让用户数据以"文本"而非"标记"身份进入解析器】
2、为什么不能只靠黑名单：【和 SQLi 同理。`<script>` 禁了还有 `<img onerror>`、
   `<svg onload>`、`<body onpageshow>`…… 黑名单永远列不全】
3、配合措施：【CSP 限制内联脚本与外部域名；Cookie 加 HttpOnly 让 JS 读不到；
   敏感操作加二次验证】
4、同类问题排查：【按"用户输入在哪几个页面/接口被输出"全面排查，
   特别注意后台管理页面（存储型最常打的地方）】
5、修复验证方法：
   【原 payload 复测，预期：被编码输出成可见文本，不执行】
   【换上下文复测：属性内 / JS 内 / URL 内，确认每种上下文都编码正确】
   【换标签复测：<img onerror>、<svg onload>，确认黑名单不是唯一防线】

### 三、延伸思考
**卡在哪**：【例：不知道数据回了哪里就开始试 payload，白试很久】
**学到什么**：【例：XSS 的难点不是 payload，是判断上下文】
```

# 三、CSRF

```markdown
## 漏洞概要
【CSRF 的本质：浏览器会自动带上目标站点的 Cookie，服务端只认 Cookie 不认"意图"，
  于是攻击者可以诱使已登录用户在自己不知情的情况下发出请求。
  与 XSS 的区别：XSS 是"在别人站点执行我的代码"，CSRF 是"借用户的身份发请求"——
  **CSRF 不需要读到任何数据，只需要用户带着 Cookie 发一次请求**。】

## 漏洞检测
0、找敏感操作【改密码、改邮箱、转账、加管理员、删除数据——只找"状态改变"的操作】
1、看是否有 CSRF Token
   【把请求发到 Repeater，删掉 token 参数 / 改成错误值 / 用另一个会话的 token，
    看是否仍能成功。三种都要试】
2、看 Token 校验是否只做"存在性"
   【有的实现只判断"token 参数在不在"，不校验值】
3、看 Cookie 的 SameSite 属性
   【Set-Cookie 里若无 SameSite 或为 None，跨站请求会带上 Cookie】
4、看 Referer / Origin 校验
   【删掉 Referer、改成同域地址、改成子域，看是否被拦】
5、构造 PoC 验证
   【写一个自动提交的 HTML 表单页面，放在另一个域（或本地文件），
    用已登录的浏览器打开，看操作是否成功执行】

## 打靶练习
【1. 确认目标操作 → 2. 抓包看有无 token → 3. 删 token 重放 →
  4. 构造 PoC 页面 → 5. 用已登录浏览器打开 PoC → 6. 确认操作生效（回目标站查数据）】

## 总结

### 一、影响与危害
【技术上能做什么：以受害者身份执行任意状态改变操作】
【本次实测到什么】【对业务意味着什么：改密码导致账号被夺 / 转账 / 加管理员后门】
**利用门槛**：【用户需处于登录态 + 访问攻击者页面；存储型 XSS 可让门槛降到 0】

### 二、修复建议
1、根本修复：【CSRF Token——服务端生成随机值绑定会话，所有状态改变请求必须携带并校验。
   原理：攻击者无法预知 token，也就无法构造出合法请求】
2、为什么只加 Referer 校验不够：【Referer 可被省略或伪造，且存在隐私策略拦截的情况】
3、配合措施：【Cookie 设 SameSite=Lax/Strict；关键操作要求重新输入密码】
4、同类问题排查：【列出所有"状态改变"接口，逐个检查是否有 token 校验】
5、修复验证方法：
   【原 PoC 复测，预期：请求被拒绝（token 缺失/错误）】
   【换手法复测：删 token、错 token、跨会话 token，确认都被拒绝】

### 三、延伸思考
```

# 四、SSRF

```markdown
## 漏洞概要
【SSRF 的本质：服务端把"用户可控的 URL"当作可信任的请求目标，
  于是攻击者能借服务端的网络位置去访问它本该访问不到的地方（内网 / 本机 / 云元数据）。
  关键点：**攻击者的请求是"从服务端发出的"，所以能绕过网络边界。**】

## 漏洞检测
0、找功能入口【URL 抓取、图片加载、文件预览、Webhook、PDF 生成、翻译、分享预览】
1、确认参数可控【参数直接是完整 URL？还是只有域名/路径（后者可利用面小）】
2、验证能发外部请求【把参数换成自己控制的地址，看是否有回连】
3、验证能访问内网【换成 127.0.0.1、内网段、云元数据地址（如 169.254.169.254）】
4、测过滤规则
   【黑名单绕过的常见变体：
     - IP 表示法：127.0.0.1 → 2130706433（十进制）/ 0177.0.0.1（八进制）/ 0x7f.0.0.1（十六进制）
     - DNS 重绑定：先用公网 IP 通过校验，再解析到内网
     - 302 跳转：先指向自己服务器，再跳内网
     - 短链接、@ 符号（http://allowed.com@evil.com）】
5、判断回显
   【有回显 → 直接读内容（最强）
    无回显 → 只能确认"能发请求"，靠时间差异或带外通道判断端口开放】

## 打靶练习
【1. 找到功能 → 2. 换成自己的监听地址确认可控 → 3. 指向内网/本机端口扫描 →
  4. 读到内容或确认差异 → 5. 试黑名单绕过变体】

## 总结

### 一、影响与危害
【技术上能做什么：探测内网、读内网服务内容、访问云元数据拿临时凭据、
  结合其它服务打内网（SSRF → RCE 的常见跳板）】
【本次实测到什么】【对业务意味着什么：内网暴露 / 云凭据泄露 / 内网服务被横向攻击】
**利用门槛**：【需要一个"服务端替你发请求"的功能；有回显时危害显著放大】

### 二、修复建议
1、根本修复：【URL 白名单（不是黑名单）+ 禁止跟随跳转 + 解析后的 IP 再校验
   （防 DNS 重绑定）】
2、为什么黑名单不行：【IP 有无穷多种等价写法，域名可解析到内网，
   跳转可绕过首次校验——黑名单在 SSRF 场景下几乎必然被绕过】
3、配合措施：【服务端出网走独立代理/网络段，禁访内网段与元数据地址；
   元数据接口改用需要 token 的版本】
4、同类问题排查：【所有"服务端发起请求且 URL 含用户输入"的地方】
5、修复验证方法：
   【原 payload 复测：内网地址、元数据地址、十进制 IP、302 跳转，
    预期：全部被拒绝或解析不到】
   【用自己的公网监听验证：确认仍能访问合法白名单地址（避免修过头）】

### 三、延伸思考
```

# 五、文件上传

```markdown
## 漏洞概要
【文件上传的本质：应用信任了"客户端提交的文件名与类型"，
  导致用户可控的内容以"可执行文件"的身份落到了服务器上。
  危害的落点是**解析**——文件能上传不等于能利用，能被当脚本执行才是 RCE。】

## 漏洞检测
0、找上传入口【头像、附件、导入、编辑器】
1、测最基础的上传【直接传 .php 文件，看是否成功、能否访问、能否执行】
2、逐层测校验
   【前端 JS 校验 → 关掉 JS 或用 Burp 直接改包（前端校验等于没有）】
   【Content-Type 校验 → 改成 image/png】
   【后缀黑名单 → 试等价后缀：.phtml / .php5 / .php3 / .pht；大小写 .PHP；双写 .pphphp；
     加壳 .php.jpg / .php%00.jpg；加点结尾 .php.（Windows 会吃掉末尾点）】
   【魔术字节校验 → 文件头加 GIF89a】
   【内容二次渲染 → 图片马需配合解析漏洞或文件包含】
3、测解析漏洞【Apache 多后缀解析、Nginx 解析配置错误、
   目录名带 .php（如 /upload/x.php/1.jpg）】
4、验证利用【访问上传后的路径 → 执行命令（如 `?cmd=whoami`）】

## 打靶练习
【按"先传最朴素的后缀 → 被拦 → 判断拦在哪一层 → 逐层绕过 → 拿到执行"写】

## 总结

### 一、影响与危害
【技术上能做什么：上传 webshell → 执行任意命令 → 控制服务器，
  进而读源码、连数据库、内网横向移动】
【本次实测到什么】【对业务意味着什么：服务器沦陷导致数据全量泄露、被当作跳板】
**利用门槛**：【上传功能开放即可；实际利用取决于校验层级与解析配置】

### 二、修复建议
1、根本修复：【白名单后缀（只允许需要的类型）+ 重命名（随机名 + 白名单后缀）+
   **存储目录不给执行权限**（这是最关键的一层）】
2、为什么黑名单不行：【后缀等价写法太多（.phtml/.pht/大小写/双写/解析漏洞），
   黑名单必然漏】
3、配合措施：【校验文件真实类型（读魔术字节，不信任 Content-Type）；
   上传目录与 Web 根分离或经 CDN/对象存储；限制上传目录的执行权限】
4、同类问题排查：【所有上传点，包括富文本编辑器、导入功能】
5、修复验证方法：
   【原 payload 复测：.php、.phtml、.PHP、.php.jpg、带魔术字节的图片马，
    预期：全部拒绝或即使上传成功也不可执行（访问返回源文件或 403）】
   【反向验证：合法图片正常上传且能正常访问（避免修过头）】

### 三、延伸思考
```

# 六、文件包含 / 目录遍历

```markdown
## 漏洞概要
【文件包含的本质：动态 `include/require` 的路径含用户输入，
  用户就能控制"加载哪个文件"——而加载的文件可以是**代码**，
  于是"读文件"升级成"执行代码"。
  目录遍历的本质：路径未归一化，`../` 能跳出限定目录。两者常组合使用。】

## 漏洞检测
0、找动态包含点【`?page=` / `?file=` / `?lang=` / `?template=`，值看起来像文件名】
1、测本地文件包含【换成 /etc/passwd 或 ../../../../etc/passwd，看是否读出内容】
2、测前缀/后缀拼接【值尾部被拼了 `.php` 时，可用伪协议或 `%00` 截断（PHP <5.3.4）】
3、测伪协议（PHP）
   【php://filter/convert.base64-encode/resource=index.php  →  读源码（无回显也能读）
     php://input（POST 内容当代码执行）
     data://text/plain;base64,xxx（直接执行代码）
     expect://（需扩展）】
4、测日志投毒（无文件上传时的组合技）
   【把 PHP 代码写进 User-Agent / Referer → 进入 Apache access.log →
    再用 LFI 包含该日志文件执行】
5、目录遍历单测【`?file=../../../../etc/passwd`，并试编码变体 %2e%2e%2f、..%5c】

## 打靶练习
【按"找到包含点 → 读普通文件确认 → 读源码确认拼接方式 → 走伪协议/日志投毒拿到执行"写】

## 总结

### 一、影响与危害
【技术上能做什么：读任意文件（源码/配置/密钥）→ 配合伪协议或日志投毒升级为 RCE】
【本次实测到什么】【对业务意味着什么：源码泄露导致漏洞暴露面扩大；
  拿到执行权限即等于服务器沦陷】
**利用门槛**：【一个路径可控的包含点；升级为 RCE 通常需要额外条件（伪协议可用/可写日志）】

### 二、修复建议
1、根本修复：【白名单映射——用户传的是"标识"（如 en/zh），
   服务端映射到固定文件路径，用户输入不参与路径拼接】
2、为什么不能只过滤 `../`：【编码变体（%2e%2e%2f、双写、%5c）、
   绝对路径、伪协议都能绕过】
3、配合措施：【关闭不必要的伪协议（allow_url_include=Off）；
   open_basedir 限制可访问目录；Web 目录不给写权限（防日志投毒）】
4、同类问题排查：【所有接收"文件名/路径/模板名"参数的地方】
5、修复验证方法：
   【原 payload 复测：/etc/passwd、../、php://filter、data://、日志文件，
    预期：全部被拒绝或返回固定白名单文件】
   【反向验证：正常语言/模板切换仍工作】

### 三、延伸思考
```

# 七、命令注入 / RCE

```markdown
## 漏洞概要
【命令注入的本质：应用把用户输入拼进系统命令，
  导致 Shell 无法区分"命令"与"参数"，用户输入被当命令执行。
  与 SQLi 完全同构——只是"隔开代码与数据"的对象从数据库换成了 Shell。】

## 漏洞检测
0、找调用点【ping / nslookup / 文件转换 / 压缩 / 图片处理 / 系统信息查询】
1、测命令拼接
   【传 `127.0.0.1; whoami`、`| whoami`、`&& whoami`、换行 `%0a whoami`、
    反引号 / `$(...)`——逐个试，判断过滤器放行了哪个】
2、测回显 vs 盲注
   【有回显 → 直接读命令输出
    无回显 → 时间盲注（`; sleep 5`）、带外（curl 到自己的监听端）】
3、测过滤规则【空格被过滤时用 ${IFS}、%09、`<`、$IFS$9】
4、验证利用【尝试反弹 shell 或写出 webshell（视权限）】

## 打靶练习
【按"找到调用点 → 试出分隔符 → 判断回显 → 执行命令 → 提权/横向"写】

## 总结

### 一、影响与危害
【技术上能做什么：以 Web 服务进程权限执行任意命令，
  读源码/配置、连数据库、写 webshell、反弹 shell → 服务器完全沦陷】
【本次实测到什么】【对业务意味着什么：单点漏洞直接导致主机失守，
  是最严重的一类；常作为内网渗透的起点】
**利用门槛**：【存在调用系统命令且拼接用户输入的功能；
  权限取决于 Web 进程的运行身份】

### 二、修复建议
1、根本修复：【不使用 Shell——用语言自带的、以**参数数组**形式调用的接口
   （如 Python 的 subprocess 传 list、PHP 的 escapeshellarg 配合白名单参数）。
   原理：不经 Shell 解析，分隔符就失去意义】
2、为什么只过滤 `;` `|` 不够：【分隔符种类多（换行、反引号、$()、&&、||），
   还有编码与通配符绕过】
3、配合措施：【能不用系统命令就不用；必须用则用白名单校验参数内容
   （如只允许 IP 地址格式）；Web 进程降权运行】
4、同类问题排查：【所有 exec/system/popen/shell_exec 类调用点】
5、修复验证方法：
   【原 payload 复测：; | && 换行 反引号 $() 全部变体，
    预期：全部被拒绝或作为普通字符串处理】
   【反向验证：正常功能（如 ping 合法 IP）仍工作】

### 三、延伸思考
```

# 八、越权（水平 / 垂直）

```markdown
## 漏洞概要
【越权的本质：应用只校验了"请求来自登录用户"，
  没有校验"这个用户是否有权操作这个对象"。
  与其它漏洞的区别：**它不是技术解析层的失守，而是业务逻辑层的失守**——
  所以没有"payload"，只有"改个 ID 试试"。】

## 漏洞检测
0、准备两个账号【A 和 B，同权限；再准备一个高权限账号 C（如果能拿到）】
1、水平越权（同级别用户互操作）
   【用 A 登录，抓取访问自己资源的请求 → 把资源 ID 改成 B 的 → 看是否返回 B 的数据】
   【要点：删 ID、改成别人的 ID、改成不存在的 ID、数组传多个 ID，四种都试】
2、垂直越权（低权限做高权限操作）
   【用 A（低权限）的会话，直接访问管理员接口（从 C 的流量里获得）
    看是否被拦】
3、越权写操作【不只是读——改资料、删资源、改状态，危害更大】
4、看是否有前端隐藏【菜单看不到 ≠ 接口不可访问，直接构造请求】

## 打靶练习
【按"两个账号 → 抓正常请求 → 改 ID → 观察到他人数据 → 扩展成写操作"写】

## 总结

### 一、影响与危害
【技术上能做什么：读取/修改/删除他人数据；低权限用户执行管理员操作】
【本次实测到什么（具体到哪个接口、改了什么参数、拿到了谁的什么数据）】
【对业务意味着什么：用户数据批量泄露；管理员功能被越权调用可能直接导致系统被控】
**利用门槛**：【只需一个普通账号；参数名可猜（id/user_id/order_id），
  往往批量遍历即可拖走全量数据】

### 二、修复建议
1、根本修复：【每次涉及对象的操作，都校验"当前登录用户是否有权操作**该对象**"
   （对象级权限校验，而不是只校验是否登录）。
   原理：把"我是谁"和"我能操作什么"分开校验，后者必须逐次验证】
2、为什么前端隐藏不行：【前端只是展示层，接口才是真实入口】
3、配合措施：【资源 ID 用不可预测的值（UUID）；会话中保存用户身份，不信任请求里的身份参数；
   敏感操作二次验证】
4、同类问题排查：【列出所有"带对象 ID 参数"的接口，逐个用双账号验证】
5、修复验证方法：
   【原 payload 复测：用 A 访问 B 的资源，预期：返回 403 / 空 / 跳转，且不泄露任何他人数据】
   【换手法复测：删 ID、改数组、跨层级（低权限访问管理接口），确认全部被拦】
   【反向验证：A 访问自己的资源仍正常】

### 三、延伸思考
```

## 附：写报告的三个自检问题

写完一份报告，问自己：

1. **成因那一问，我能不能讲 30 秒不停、且不说"就是没过滤"？**
2. **修复验证方法，别人照着做能不能独立判断"修好了没有"？**
3. **有没有哪个结论是我"推断"但没实测的？** 有就补测，或删掉。

> 一份报告的价值不在于"指出了多少问题"，而在于**读者能不能据此复现、
> 并确认问题真的被修好了**。
